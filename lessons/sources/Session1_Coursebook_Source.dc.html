Refresher · the four ideas every lesson builds on
  • Tokens & next-token prediction. Text becomes tokens (integer IDs); the model outputs a logit per vocabulary entry and a softmax gives pθ(xt | x<t), the probability of the next token. θ = all trainable parameters. Generation = pick a token, append, repeat.
  • One transformer layer. L identical layers; in each, every token computes Query, Key and Value vectors (Q = XWQ, K = XWK, V = XWV) and attends to earlier tokens: Attention(Q,K,V) = softmax(QKᵀ/√dk)·V, in H heads of width dh (dmodel = H·dh), then a small MLP. The K and V of every past token, per layer and head, are what the KV-cache (Lesson 5) stores.
  • What training changes. A loss — for LLMs the cross-entropy 𝓛(θ) = −Σt log pθ(xt | x<t) — is minimised by repeating forward pass → loss → backward pass (gradient ∂𝓛/∂θ) → optimizer step θ ← θ − learning rate × gradient. A batch = the examples in one step; an epoch = one pass over the data. Fine-tuning is this loop from the pretrained θ on your data (with LoRA, on a few extra parameters).
  • Training vs inference. Training sees the whole sequence at once (teacher forcing); inference generates one token at a time and feeds it back — so decoding rules and the KV-cache only matter at serving time.
Lesson 1 · Adapting

Supervised fine-tuning & the epochs trap

Objective · why longer training makes the model worse

SFT is imitation: you show the model (prompt, response) pairs and it copies the format. The counter-intuitive part for most people is that training longer makes it worse. After the first one to three epochs the model has stopped learning the skill and started memorising your examples — quietly overwriting the broad, general ability it arrived with.

Two failure modes ride together: catastrophic forgetting (general skills get pressed out) and style overfitting (it memorises the shape — always three bullets, always the same length — without the underlying skill). The fix is boring and reliable: 1–3 epochs, a low learning rate, and mix 10–20% general data back in.

Anchor it
More epochs is not more learning — it is more forgetting.
What the trainer minimises
For a prompt x and a response y = (y1, …, yT):  𝓛SFT(θ) = − Σt=1..T log pθ(yt | x, y<t) — the pretraining cross-entropy on curated data, where x is the prompt as the model's chat template lays it out and θ the trainable parameters (with LoRA, the adapter). Loss masking: the sum runs over response tokens only; prompt tokens get label −100 (TRL does this from the prompt/completion fields with completion_only_loss=True). Same template at training and inference, or the model looks worse although the weights are fine. SFT shapes behaviour; it does not add facts.
# 1 epoch, low LR — resist the urge to run it for 20
args = SFTConfig(output_dir="./adapter", num_train_epochs=1,
                 learning_rate=2e-5, lr_scheduler_type="cosine",
                 warmup_steps=10, per_device_train_batch_size=2,
                 gradient_accumulation_steps=8, max_length=1024,
                 completion_only_loss=True,   # loss on the response tokens only
                 bf16=use_bf16, fp16=(device == "cuda" and not use_bf16))

Lesson 2 · Adapting

Beyond imitation: GRPO & group-relative advantage

Objective · why we divide by the group's standard deviation

SFT can't optimise “is this correct?” or “is this safe?” — those aren't clean labels in the data. GRPO can. It samples a group of answers to the same prompt, scores each, then standardises within the group before using the scores:

Aij = ( rij − μi ) / ( σi + ε )

For prompt i with a group of G sampled answers: rij = the reward of answer j · μi = the group's mean reward · σi = its standard deviation · ε = a small constant that avoids dividing by zero · Aij = the advantage, how much better answer j is than its siblings. The group is the baseline, so no separate value network (critic) is needed.

Subtracting the mean says whether an answer is better or worse than its siblings. Dividing by σ is the part people skip, and it's the part that makes training stable: it puts every prompt group on the same scale, so “clearly the best answer here” counts equally whether rewards ran 1–5 or were bunched between 4 and 5. Every prompt type gets an equal vote in the update.

PromptRewardsμσBest, mean-subtractedBest, standardised
Safety-critical0.5 · 5.0 · 1.0 · 4.5 · 2.0 · 5.03.001.89+2.00+1.06
Simple definition4.0 · 4.2 · 4.5 · 4.1 · 4.3 · 4.04.180.18+0.32+1.79

Mean-subtracted only, the definition prompt's best answer carries a 6× weaker signal than the safety prompt's, so the optimiser effectively ignores it; standardised, both get a clear positive advantage of comparable size.

# standardise rewards within each group:  A_ij = (r_ij - mu_i) / (sigma_i + eps)
def group_advantage(rewards, eps=1e-6, divide_by_sigma=True):
    rewards = np.asarray(rewards, float)
    centred = rewards - rewards.mean()
    return centred / (rewards.std() + eps) if divide_by_sigma else centred

group_advantage([0.5, 5.0, 1.0, 4.5, 2.0, 5.0])  # safety-critical: wide spread
group_advantage([4.0, 4.2, 4.5, 4.1, 4.3, 4.0])  # definition: bunched
The trick
Subtract the mean for direction, divide by sigma for a comparable size. Skip the division and your best-behaved prompts quietly stop teaching the model anything.
The rest of the GRPO update
The advantages feed a PPO-style objective: the policy πθ is nudged to make high-advantage answers more likely through a clipped probability ratio ρij = πθ(yij | qi) / πθold(yij | qi), and a KL penalty with weight β keeps it near the SFT reference πref: 𝓛(θ) = E[min(ρijAij, clip(ρij, 1−εclip, 1+εclip)Aij)] − β·KL(πθ ‖ πref). The notebook does not run this loop (it needs TRL's GRPOTrainer and a GPU budget); it isolates standardisation and reward design.
Lesson 3 · Adapting

Reward design & reward hacking

Objective · keep correctness and safety on separate axes

If you collapse correctness and safety into one number, the model can look great while quietly gaming one dimension — high correctness, dangerous safety, and a single reward that hides it. This is reward hacking: the model optimises the metric, not the intent.

Keep them separate, put a floor on safety, and you can actually see which dimension is being gamed instead of averaging the problem away.

✗ Collapsed
r = 0.7*correct + 0.3*safe

Scores run 1–5. A perfectly correct (5) but dangerous (1) answer gets 3.8 — looks “fine”, ships anyway.
✓ Separate + floor
r = 0.7*correct + 0.3*safe
if safe < 4:
    r = r - 5   # hard penalty

The same answer now scores −1.2. Unsafe is unsafe, full stop; each axis stays visible.
Rule of thumb
One number per thing you care about, a floor on the non-negotiable one, and never average safety into oblivion.
Lesson 4 · Adapting

LoRA & QLoRA: winning twice

Objective · LoRA is a regulariser AND a serving superpower

LoRA freezes the big pretrained weight and learns a small low-rank correction next to it. Two wins, said explicitly:

  • Win 1 · Regulariser. Few free parameters ⇒ the model can only change the most important directions ⇒ it overfits less on ~20k samples.
  • Win 2 · Serving. One base model on the GPU + tiny hot-swappable adapters. Three behaviours = one base + three adapters, not three full copies.
The maths, in one line
A linear layer computes h = W·x with a frozen W ∈ ℝdout×din. LoRA adds a low-rank correction:  h = W·x + ΔW·x,  ΔW = (α/r)·B·A,  B ∈ ℝdout×r, A ∈ ℝr×din, r ≪ d. r = the rank (r=16), α = lora_alpha (32), so the update is scaled by α/r = 2; only A and B get gradients; A random and B = 0 at init so training starts exactly at the base model. Parameter count: r·(din + dout) instead of din·dout per adapted matrix (2·d·r vs d² when square): Qwen's 896×896 q_proj at r = 16 trains 28,672 numbers instead of 802,816 (3.6%); over 7 matrices × 24 layers the adapter is 8.8 M parameters, ≈ 1.8% of the base. QLoRA keeps the frozen W in 4-bit NF4 and dequantises it on the fly: h = dequant(Ŵ)·x + ΔW·x.
# QLoRA: 4-bit frozen base, train a tiny low-rank adapter
# ONE source of truth for every dtype — a T4 is sm_75 and cannot train bf16:
use_bf16 = device == "cuda" and torch.cuda.get_device_capability()[0] >= 8
compute_dtype = torch.bfloat16 if use_bf16 else torch.float16

bnb = BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type="nf4",
        bnb_4bit_compute_dtype=compute_dtype, bnb_4bit_use_double_quant=True)
model = AutoModelForCausalLM.from_pretrained(BASE, quantization_config=bnb,
        dtype=compute_dtype, device_map="auto")   # never dtype="auto"

lora = LoraConfig(r=16, lora_alpha=32, lora_dropout=0.05,
        bias="none", task_type="CAUSAL_LM",
        target_modules=["q_proj","k_proj","v_proj","o_proj",
                        "gate_proj","up_proj","down_proj"])

# SFTTrainer force-casts QLoRA adapters to bf16. On a T4 (fp16 + GradScaler)
# there is no bf16 unscale kernel, so put the adapter back in fp32.
if not use_bf16:
    for p in trainer.model.parameters():
        if p.requires_grad and p.dtype == torch.bfloat16:
            p.data = p.data.to(torch.float32)

In the lab: pick a base model and a LoRA rank r — the trainable-params counter shows how little actually trains (often well under 1%).

The T4 bfloat16 trap
A Colab T4 is compute capability 7.5, so it trains in fp16 with a GradScaler, which has no bfloat16 kernel. Transformers 5 (dtype="auto" reads Qwen's bfloat16 config), bnb_4bit_compute_dtype and SFTTrainer (which force-casts QLoRA adapters to bf16) will each hand you bf16 regardless. Derive all of them from one capability check and re-check the adapter dtype afterwards.
Lesson 5 · Serving

The KV-cache: the memory nobody budgets for

Objective · why serving falls over, and why vLLM exists

When people plan GPU memory they count the model weights and stop. Then a few users send long prompts and the server falls over. The thing they forgot is the KV-cache. Attention needs the Key and Value vectors of every earlier token; recomputing them for each new token would make generation quadratic, so the server keeps them — one K and one V per token, in every layer, for every key/value head. It grows with sequence length × layers × heads and can dwarf the weights.

MKV ≈ 2 · S · L · Hkv · dh · b/8  bytes per sequence

S = sequence length (prompt + generated) · L = layers · Hkv = key/value heads (= H, the attention heads, unless the model uses GQA/MQA) · dh = head dimension · b = bits per value (16 for FP16); the 2 is one Key + one Value tensor. For B concurrent sequences multiply by B.

Worked example
13B model (L = 40, H = 40, dh = 128), FP16, S = 4096: 2 · 4096 · 40 · 40 · 128 · 2 bytes = 3,355,443,200 bytes ≈ 3.36 GB for a single sequence, next to ≈ 26 GB of weights; 64 users at that context need ≈ 215 GB of cache. The weights are fixed — the cache scales with context × users, which is why long-context serving is dominated by the cache.

Two ways to shrink it: store the cache in INT8 (b = 8, roughly halves it), or use grouped-query attention so query heads share Keys and Values (Hkv ≪ H; Qwen2.5-0.5B has 14 query heads but only 2 KV heads). And this is the whole reason vLLM exists — next lesson.

Lesson 6 · Serving

Serving at scale: vLLM & PagedAttention

Objective · page the cache like OS virtual memory

The naive server reserves one big contiguous block of cache per request, sized for the worst case — so most of it sits empty and you run out of room long before you run out of GPU. PagedAttention stores the KV-cache in small non-contiguous blocks, handed out on demand exactly like operating-system virtual memory. Waste drops to almost nothing, and the same card serves far more users. Continuous batching lets new requests join a running batch as others finish. The vLLM paper (Kwon et al., 2023) reports ≈ 24× the throughput of a naive 🤗 generate loop with under 4% of the cache wasted.

# PagedAttention + prefix caching + hot-swappable LoRA
# Runs in the SEPARATE vLLM environment, never in the training runtime.
# float16 + 0.80 fit a 16 GB T4; use bfloat16 on Ampere or newer.
llm = LLM(model="Qwen/Qwen2.5-0.5B-Instruct", dtype="float16",
          gpu_memory_utilization=0.80,
          enable_prefix_caching=True,
          enable_lora=True, max_model_len=2048)
sp = SamplingParams(temperature=0.2, top_p=0.9, max_tokens=128)

Lesson 7 · Serving

Grounding answers with RAG

Objective · answer from retrieved context, cite or say “unknown”

Fine-tuning teaches a skill; it doesn't install facts. For grounded, up-to-date, citable answers you retrieve relevant context at query time and instruct the model to use only that context — or admit it doesn't know. The flow: question → embed & retrieve top-k → stuff context + cite → grounded answer. An embedding model (all-MiniLM-L6-v2) maps any text to a 384-dimensional vector so similar meanings land close together; the corpus is embedded once, the question is embedded at query time, and the top-k passages by cosine similarity that pass a gate are pasted into the prompt with citation tags [0], [1], … (nothing above the gate → "no relevant passages found"); after generation the citation is checked against that list. A vector database (FAISS, Milvus) does the same retrieval at scale.

# retrieve -> gate -> cited context -> generate -> check the citation
embed = SentenceTransformer("all-MiniLM-L6-v2")
C = embed.encode(corpus, convert_to_tensor=True)
scores = util.cos_sim(embed.encode(q, convert_to_tensor=True), C)[0]
docs = [corpus[i] for s, i in zip(*scores.topk(k)) if float(s) >= MIN_SIM]   # gate: 0.35

ctx = "\n".join(f"[{i}] {d}" for i, d in enumerate(docs)) or "(no relevant passages found)"
prompt = (f"Context:\n{ctx}\n\nQuestion: {q}\n\n"
          "Rules:\n1. Answer in one or two sentences using ONLY the context above.\n"
          "2. Finish with the citation of the item you used, e.g. [0].\n"
          "3. If the context does not contain the answer, reply with exactly: unknown\n\n"
          'Example of a grounded answer: "Beam search keeps k candidates. [1]"\n'
          'Example when the context does not help: "unknown"\n\nAnswer:')

ids = tok(tok.apply_chat_template([{"role": "user", "content": prompt}],
          tokenize=False, add_generation_prompt=True), return_tensors="pt")
out = trainer.model.generate(**ids.to(trainer.model.device), max_new_tokens=96,
                             do_sample=False, repetition_penalty=1.0)   # copying must not be penalised
raw = tok.decode(out[0, ids["input_ids"].shape[1]:], skip_special_tokens=True).strip()
cited = [int(i) for i in re.findall(r"\[(\d+)\]", raw)]
print(raw if cited and all(i < len(docs) for i in cited) and not raw.lower().startswith("unknown") else "unknown")
The guardrail is the prompt
“Use ONLY the context; cite [i] or say unknown.” Grounding, a retrieval gate, citations that are checked, and a permission to refuse are what make an assistant trustworthy.
