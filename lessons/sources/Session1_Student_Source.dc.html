Refresher · the four ideas every lesson builds on
1 · Tokens & next-token prediction. Text is split into tokens (integer IDs). The model reads the tokens so far, outputs a logit per vocabulary entry, and a softmax turns them into pθ(xt | x<t), the probability of the next token; θ is the set of all trainable parameters. Generation = pick a token, append it, repeat.
2 · One transformer layer. L identical layers. In each, every token computes a Query, Key and Value vector (Q = XWQ, K = XWK, V = XWV) and attends to earlier tokens: Attention(Q,K,V) = softmax(QKᵀ/√dk)·V, in H heads of width dh (dmodel = H·dh), followed by a small MLP. The K and V of every past token, per layer and head, are what the KV-cache of Lesson 5 stores.
3 · What training changes. A loss — for LLMs the cross-entropy 𝓛(θ) = −Σt log pθ(xt | x<t) — is minimised by repeating: forward pass → loss → backward pass (gradient ∂𝓛/∂θ) → optimizer step θ ← θ − learning rate × gradient. A batch is the set of examples in one step; an epoch is one pass over the data. Fine-tuning is the same loop started from the pretrained θ on your data — with LoRA, on a few extra parameters instead of θ.
4 · Training vs inference. Training sees the whole sequence at once (teacher forcing). Inference generates one token at a time and feeds it back — which is why decoding rules (Lesson 5) and the KV-cache only matter at serving time.

Lesson 1 · Adapting

Supervised Fine-Tuning & the epochs trap

Objective · why longer training makes the model worse

SFT is imitation: you show the model (prompt, response) pairs and it copies the format. The counter-intuitive part for most people is that training longer makes it worse. After the first one to three epochs the model has stopped learning the skill and started memorising your examples — quietly overwriting the broad, general ability it arrived with.

Two failure modes ride together: catastrophic forgetting (general skills get pressed out) and style overfitting (it memorises the shape — always three bullets, always the same length — without the underlying skill). The fix is boring and reliable: 1–3 epochs, a low learning rate, and mix 10–20% general data back in.

Anchor it: more epochs is not more learning — it is more forgetting.
What the trainer actually minimises

SFT is the pretraining objective on curated data. For a prompt x and a response y = (y1, …, yT) the loss is the negative log-probability of each response token given everything before it:

𝓛SFT(θ) = − Σt=1..T log pθ( yt | x, y<t )
  • •x = the prompt as the model's chat template lays it out (system + user turns) · yt = the t-th response token · θ = the trainable parameters (with LoRA, only the adapter).
  • •Loss masking. The sum runs over response tokens only; prompt tokens get the label −100 and contribute nothing. In the notebook TRL builds that mask because the data is handed over as prompt / completion fields with completion_only_loss=True.
  • •Same template at training and inference. TRL serialises every example with the tokenizer's chat template, and Lesson 7 prompts through the same template. Train on one format and prompt with another and the model looks “worse” although the weights are fine.
  • •Notice: nothing here adds knowledge — SFT is behaviour shaping. Facts come from retrieval (Lesson 7).

Lesson 2 · Adapting

Beyond imitation: GRPO & group-relative advantage

Objective · why we divide by the group's standard deviation

SFT can't optimise “is this correct?” or “is this safe?” — those aren't clean labels in the data. GRPO can. It samples a group of answers to the same prompt, scores each, then standardises within the group before using the scores:

Aij = ( rij − μi ) / ( σi + ε )

For prompt i with a group of G sampled answers: rij = the reward of answer j · μi = the mean reward of the group · σi = its standard deviation · ε = a small constant that avoids dividing by zero · Aij = the advantage: how much better answer j is than its siblings. The group is the baseline, so no separate value network (critic) is needed.

Subtracting the mean is the obvious part — it says whether an answer is better or worse than its siblings. Dividing by σ is the part people skip, and it's the part that makes training stable: it puts every prompt group on the same scale, so “clearly the best answer here” counts equally whether rewards ran 1–5 or were bunched between 4 and 5.

notebooks/session1.ipynb · group-relative advantage 
# standardise rewards within each group:  A_ij = (r_ij - mu_i) / (sigma_i + eps)
def group_advantage(rewards, eps=1e-6, divide_by_sigma=True):
    rewards = np.asarray(rewards, float)
    centred = rewards - rewards.mean()
    return centred / (rewards.std() + eps) if divide_by_sigma else centred

group_advantage([0.5, 5.0, 1.0, 4.5, 2.0, 5.0])  # safety-critical: wide spread
group_advantage([4.0, 4.2, 4.5, 4.1, 4.3, 4.0])  # definition: bunched
# pass divide_by_sigma=False and watch the definition row collapse
The rest of the GRPO update. The advantages feed a PPO-style objective: the policy πθ is nudged to make high-advantage answers more likely through a clipped probability ratio ρij = πθ(yij | qi) / πθold(yij | qi), and a KL penalty with weight β keeps it close to the SFT reference model πref:
𝓛(θ) = E[ min(ρij Aij, clip(ρij, 1−εclip, 1+εclip) Aij) ] − β · KL(πθ ‖ πref)Group size G, sampling temperature, εclip and β are the knobs. The notebook does not run this loop (it needs TRL's GRPOTrainer and a GPU budget); it isolates the two ideas that decide whether it works — standardisation (this lesson) and reward design (next).
Lesson 3 · Adapting

Reward design & reward hacking

Objective · keep correctness and safety on separate axes

If you collapse correctness and safety into one number, the model can look great while quietly gaming one dimension — high correctness, dangerous safety, and a single reward that hides it. This is reward hacking: the model optimises the metric, not the intent.

Keep them separate, put a floor on safety, and you can actually see which dimension is being gamed instead of averaging the problem away.

✗ Collapsed
r = 0.7·correct
    + 0.3·safe

Scores run 1–5. A perfectly correct (5) but dangerous (1) answer gets 0.7·5 + 0.3·1 = 3.8 — looks “fine”, ships anyway, and nothing in the number says why.

✓ Separate + floor
r = 0.7·correct + 0.3·safe
if safe < 4:
  r = r − 5  # hard penalty

The same answer now scores −1.2. Unsafe is unsafe, full stop — and because correctness and safety are scored separately you can watch each axis move on its own.

Rule of thumb: one number per thing you care about, a floor on the non-negotiable one, and never average safety into oblivion.
notebooks/session1.ipynb · reward with a safety floor 
# keep the signals separate, enforce a safety floor, then standardise per group
def reward(correctness, safety, alpha=0.7, safety_floor=4.0):
    r = alpha*correctness + (1-alpha)*safety
    return np.where(safety < safety_floor, r - 5.0, r)   # hard penalty below the floor

drug   = reward(np.array([5,4,1,2]), np.array([5,2,5,1]))   # -> [ 5.  -1.6  2.2 -3.3]
define = reward(np.array([5,5,4,5]), np.array([5,5,5,5]))   # -> [ 5.   5.   4.3  5. ]
group_advantage(drug), group_advantage(define)              # both on the same ±scale
Lesson 4 · Adapting

LoRA & QLoRA: winning twice

Objective · LoRA is a regulariser AND a serving superpower

LoRA freezes the big pretrained weight and learns a small low-rank correction next to it. Say the two wins explicitly:

Win 1 · Regulariser

Few free parameters ⇒ the model can only change the most important directions ⇒ it overfits less on ~20k samples.

Win 2 · Serving

One base model on the GPU + tiny hot-swappable adapters. Three behaviours = one base + three adapters, not three full copies.

The maths, in one line

A linear layer computes h = W·x with a frozen pretrained weight W ∈ ℝdout × din. LoRA leaves W alone and adds a low-rank correction next to it:

h = W·x + ΔW·x , ΔW = (α / r) · B·A , B ∈ ℝdout × r, A ∈ ℝr × din, r ≪ d
  • •r = the rank (r=16) · α = lora_alpha (32), so the update is scaled by α/r = 2 · only A and B receive gradients. In the square case, this is written as h = Wx + BAx with B ∈ ℝd×r, A ∈ ℝr×d — the same thing with din = dout = d.
  • •Init trick: A random, B = 0 ⇒ ΔW = 0 at step 0, so training starts exactly at the base model.
  • •Parameter count: r·(din + dout) per adapted matrix instead of din·dout (2·d·r vs d² when square). Tiny example: din = dout = 8, r = 2 → 32 numbers instead of 64. Qwen's q_proj is 896×896: with r = 16 that is 28,672 instead of 802,816 (3.6%). Summed over the 7 target matrices of all 24 layers the adapter has 8.8 M parameters, ≈ 1.8% of the 494 M base — the widget below does this arithmetic for you.
  • •QLoRA = the same adapters on a base whose frozen W is stored in 4-bit NF4 and dequantised on the fly for each matmul: h = dequant(Ŵ)·x + ΔW·x. The base shrinks ≈ 4× vs FP16 while the adapters stay in higher precision — that is what fits a 13B model on one 16 GB card.

        bias="none", task_type="CAUSAL_LM",
        target_modules=["q_proj","k_proj","v_proj","o_proj",
                        "gate_proj","up_proj","down_proj"])

# SFTTrainer force-casts QLoRA adapters to bf16. On a T4 (fp16 + GradScaler)
# there is no bf16 unscale kernel, so put the adapter back in fp32.
if not use_bf16:
    for p in trainer.model.parameters():
        if p.requires_grad and p.dtype == torch.bfloat16:
            p.data = p.data.to(torch.float32)
The T4 bfloat16 trap. A Colab T4 is compute capability 7.5, so it trains in fp16 with a GradScaler — and the scaler has no bfloat16 kernel. Three separate things will hand you bf16 anyway: Transformers 5 defaults to dtype="auto" (Qwen's config says bfloat16), bnb_4bit_compute_dtype, and SFTTrainer, which force-casts QLoRA adapters to bf16 after you build it. Derive all three from one capability check, then re-check the adapter dtype — otherwise the first optimizer step raises NotImplementedError … not implemented for 'BFloat16'.
Lesson 5 · Serving

The KV-cache: the memory nobody budgets for

Objective · why serving falls over, and why vLLM exists

When people plan GPU memory they count the model weights and stop. Then a few users send long prompts and the server falls over. The thing they forgot is the KV-cache: every token already seen keeps a Key and a Value vector, in every layer, for every attention head. It grows with sequence length × layers × heads — and can dwarf the weights.

Why the cache exists, and how big it is

Attention needs the Key and Value vectors of every earlier token (refresher, idea 2). Recomputing them for each new token would make generation quadratic, so the server keeps them: one K and one V vector per token, per layer, per key/value head. That store is the KV-cache, and it grows with the sequence:

MKV ≈ 2 · S · L · Hkv · dh · b/8 bytes per sequence
  • •S = sequence length (prompt + generated tokens) · L = layers · Hkv = key/value heads (equal to H, the attention heads, unless the model uses GQA/MQA) · dh = head dimension · b = bits per value (16 for FP16). The 2 is one Key tensor + one Value tensor. For B concurrent sequences multiply by B.
  • •Worked example — a 13B model (L = 40, H = 40, dh = 128), FP16, S = 4096: 2 · 4096 · 40 · 40 · 128 · 2 bytes = 3,355,443,200 bytes ≈ 3.36 GB for a single sequence, next to ≈ 26 GB of weights. 64 users at that context need ≈ 215 GB of cache.
  • •Notice: the weights are fixed; the cache scales with context × users. Long-context serving is dominated by the cache, not the weights — the calculator below shows the crossover.

Lesson 6 · Serving

Serving at scale: vLLM & PagedAttention

Objective · page the cache like OS virtual memory

The naive server reserves one big contiguous block of cache per request, sized for the worst case — so most of it sits empty and you run out of room long before you run out of GPU. PagedAttention stores the KV-cache in small non-contiguous blocks, handed out on demand exactly like operating-system virtual memory. Waste drops to almost nothing, and the same card serves far more users. Continuous batching adds the second half: new requests join a running batch as others finish instead of waiting for the whole batch to end. The vLLM paper (Kwon et al., 2023) reports ≈ 24× the throughput of a naive 🤗 generate loop with under 4% of the cache wasted.

NAIVE · contiguous

One request reserves the whole worst-case block. The striped space is wasted.

PAGED · blocks on demand

Three requests (teal / amber / blue) share the pool block-by-block. Almost no waste.

Lesson 7 · Serving

Grounding answers with RAG

Objective · answer from retrieved context, cite or say “unknown”

Fine-tuning teaches a skill; it doesn't install facts. For grounded, up-to-date, citable answers you retrieve relevant context at query time and instruct the model to use only that context — or admit it doesn't know.

How retrieval works. An embedding model (all-MiniLM-L6-v2) maps any text to a 384-dimensional vector so that similar meanings land close together. The corpus is embedded once; at query time the question is embedded, its cosine similarity to every corpus vector is computed, and the top-k passages that pass a similarity gate are pasted into the prompt with citation tags [0], [1], … (a question the corpus cannot answer gets an explicit "no relevant passages found" instead of filler). After generation the citation is checked against that list, so a bluffed "[0]" cannot reach the user. A vector database (FAISS, Milvus) does the same retrieval at scale.

Question→ Embed, retrieve top-k, gate→ Stuff context + cite→ Check citation → answer
notebooks/session1.ipynb · retrieve → cite → generate 
# retrieve -> gate -> cited context -> generate -> check the citation
embed = SentenceTransformer("all-MiniLM-L6-v2")
C = embed.encode(corpus, convert_to_tensor=True)
scores = util.cos_sim(embed.encode(q, convert_to_tensor=True), C)[0]
docs = [corpus[i] for s, i in zip(*scores.topk(k)) if float(s) >= MIN_SIM]   # gate: 0.35 on this corpus

ctx = "\n".join(f"[{i}] {d}" for i, d in enumerate(docs)) or "(no relevant passages found)"
prompt = (f"Context:\n{ctx}\n\nQuestion: {q}\n\n"
          "Rules:\n1. Answer in one or two sentences using ONLY the context above.\n"
          "2. Finish with the citation of the item you used, e.g. [0].\n"
          "3. If the context does not contain the answer, reply with exactly: unknown\n\n"
          'Example of a grounded answer: "Beam search keeps k candidates. [1]"\n'
          'Example when the context does not help: "unknown"\n\nAnswer:')

ids = tok(tok.apply_chat_template([{"role": "user", "content": prompt}],
          tokenize=False, add_generation_prompt=True), return_tensors="pt")
out = trainer.model.generate(**ids.to(trainer.model.device), max_new_tokens=96,
                             do_sample=False, repetition_penalty=1.0)   # copying prompt tokens must not be penalised
raw = tok.decode(out[0, ids["input_ids"].shape[1]:], skip_special_tokens=True).strip()
cited = [int(i) for i in re.findall(r"\[(\d+)\]", raw)]
print(raw if cited and all(i < len(docs) for i in cited) and not raw.lower().startswith("unknown") else "unknown")
The guardrail is the prompt: “use ONLY the context; cite [i] or say unknown.” Grounding, a retrieval gate, citations that are checked, and a permission to refuse are what make an assistant trustworthy.
